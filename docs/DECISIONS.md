# Decisions

## 2026-10-27: Persist repository config status on changes and config pushes

The webhook gate writes a repository's reported config status to Workers KV when it differs from the previously read status, including missing or expired entries, or after a config-changing push. Config-changing pushes always reconcile durable status even when a cached value matches the kernel response. Configured events continue to reach the kernel; ordinary unchanged responses consume no status PUT and do not refresh the response cache.

Keep the existing five-minute repository cache and 24-hour KV TTL. Cache misses read durable state, and the next event renews an expired KV entry. Preserve config-changing push bypass, present/absent transitions, organization config version invalidation, signature verification, and dispatch behavior.

## 2026-10-27: Independent account probe and burst cooldowns

For signed unknown or absent repository events, use a native rate-limit binding keyed by normalized account owner, existing organization config version, and durable owner generation, configured for 30 requests per 60 seconds. Count requests before enforcing the short missing-config probe deadline. Burst cooldowns start at 900 seconds and double independently of missing-config probe delays, which start at 30 seconds. Both progressions cap at 30 days and persist in separate generation-scoped owner probe/burst KV keys without expiry, avoiding same-key write throttling when an absent probe is immediately followed by a burst. A cold owner lookup costs three KV reads: generation, probe, and burst. Each penalty transition writes only its progression key. Recovery writes one fresh generation and cleans up both old progression keys with one DELETE each. Active cooldown denials neither rewrite state nor extend deadlines. Known-absent repositories retain the existing 24-hour status lifetime; ordinary known-present traffic captures only the cached generation and bypasses progression reads and the limiter. Config-changing pushes bypass both cooldowns and force current-generation repository status reconciliation despite stale caches. Organization config pushes also preserve the existing version invalidation.

Only confirmed 404 responses for every environment candidate in both organization and repository scopes establish absence. Existing empty/invalid files and non-404 failures remain unconfirmed; the extra confirmation reads occur only when configuration loading found no sources or plugins. Missing or throwing native rate-limit bindings return retriable HTTP 503 for unknown/absent traffic without adding a penalty, while configured repositories remain exempt. Preserve the other existing KV/cache failure boundaries. This prevents a platform limiter outage from creating false account bans.

Cache probe and burst progressions independently, matching their separate durable records. An absent response rereads current progression state after the awaited kernel call before advancing the probe delay. Publishing a completed probe PUT updates only its probe cache entry, so it cannot overwrite a burst established while the request was in flight. Use the stable initial generation when the durable generation key is missing. Recovery persists a fresh unique generation before acknowledging a reset, publishing new-generation caches, or cleaning up old keys. Generation PUT failure returns retriable HTTP 503; a present probe cannot cache successful recovery before this write succeeds. Progression keys, cache IDs, and native limiter keys include generation, so ordinary config recovery also starts a fresh native bucket. Negative responses from a superseded admission generation do not persist stale config status or penalties. Positive present confirmations still reconcile their own repository when another recovery rotates the shared generation, without repeating an obsolete owner reset. A progression PUT that finishes after its generation was replaced is ignored and its obsolete key receives one bounded cleanup DELETE. This provides a durable reset fence without process-memory-only state, retries, scheduling, or a global transaction guarantee; generation visibility still follows KV eventual consistency and the existing 60-second owner cache duration.

Isolate memory and the Workers Cache API optimize KV access; durable KV remains the fallback. Cache missing repository KV lookups with a distinct unknown sentinel for 30 seconds, using the existing memory-cache duration. This prevents repeated reads for the same denied unknown repository without persisting absence or suppressing an otherwise eligible kernel probe; config-changing pushes still bypass cooldowns and reconcile immediately. The native limiter is approximate and per Cloudflare location, and KV is eventually consistent, so this is not a strict global counter or globally serialized cooldown. Preserve current account settings without billing changes, scheduling, or new services. Keep the five-minute known-repository cache, 24-hour repository KV TTL, transition-only status writes, and forced config-push reconciliation from the earlier decision.

Capture a cached generation for all signed repository admissions, including known-present traffic, so delayed negative responses cannot adopt a post-reset generation. A configured request adds one cold generation KV GET and zero warm KV operations, while bypassing progression reads and the limiter. Cache fills compare the memory slot observed before an awaited read with the current published slot and preserve a newer publication synchronously. Apply this optimization to both generation and progression KV fills and to Cache API reads; durable KV still owns the reset fence. An expired local entry is retained only as a publication identity until replaced, and is not served as a cache hit. Reread current progressions after an awaited limiter result or kernel response before changing penalties or acknowledging recovery.
